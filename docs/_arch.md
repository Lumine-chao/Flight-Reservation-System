**1 文档概述**

**1.1 编写目的**

本文档描述航班预订系统的技术架构、技术选型、模块划分、数据设计、接口设计、安全设计与部署方案，用于指导系统开发实施与后续维护，并作为开发、测试、运维各方的技术共识基线。

系统定位为面向终端旅客的在线机票预订平台，客户自助完成注册、登录、查询、下单与订单管理全流程。架构围绕这一业务形态，重点解决账号体系、数据隔离与订单状态流转三类技术问题。

本文档中的需求编号沿用《航班预订系统项目说明文档》的编号体系：UR
为账号类需求，LR 为登录类需求，OR 为订单类需求。

本文档已完成与《航班预订系统项目说明文档》V1.0
的逐条覆盖核对，各章节均按需求编号标注落点，可据此开展需求与测试用例的双向追溯。

**1.2 架构设计要点**

本系统的架构围绕以下七个要点展开，是理解后续各章的主线：

  ---------------------------------------------------------------------------------------
  **要点**         **设计决策**
  ---------------- ----------------------------------------------------------------------
  主体数据模型     以 user（客户）为登录主体，订单通过 user_id
                   归属客户，乘机人信息作为订单属性记录

  认证机制         完整账号体系：注册 + 登录 + 安全问题重置密码，密码与安全问题答案均
                   BCrypt 加密存储，JWT 无状态会话，失败锁定

  密码策略         一人一密，注册时自设；强度校验 8～20
                   位且含字母与数字；忘记密码通过安全问题验证重置

  订单归属与隔离   订单强绑定 user_id，全链路强制隔离，从数据访问层杜绝越权

  订单状态         引入状态机与流转控制，服务端统一驱动，前端只提交动作不提交状态

  外部依赖最小化   本期不接入支付与短信等外部服务，订单金额仅作展示，降低联调与资质成本

  状态流转留痕     每次状态变更写入
                   order_status_log，记录操作人、操作时间与触发来源（客户 / 系统 /
                   管理员）
  ---------------------------------------------------------------------------------------

**1.3 技术栈说明**

本文档按「Java 后端 + Vue 前端 + 关系型数据库 +
Redis」的主流企业级技术栈编写。技术栈具备生态成熟、组件可替换、易于维护的特点，能够覆盖本系统的功能与非功能需求。若项目实际采用其他语言或框架，可按下文分层逐层替换，架构分层、模块划分、数据模型与接口契约部分保持不变。

**2 架构总览**

**2.1 架构设计原则**

  --------------------------------------------------------------------------------------------------------------------------------------------
  **原则**           **说明**                                       **在本系统中的落地方式**
  ------------------ ---------------------------------------------- --------------------------------------------------------------------------
  分层解耦           表现、应用、领域、基础设施各司其职，单向依赖   Controller 不写业务逻辑，业务规则集中在领域层与校验器

  规则内聚           校验规则与提示语集中管理                       用户名、密码强度、安全问题、日期、同城等规则统一由 Validator
                                                                    承载，提示语集中配置

  接口先行           前后端通过明确的 REST 契约协作                 所有功能以 REST API 暴露，统一响应包装与错误码

  无状态服务         服务本身不保存会话状态，便于水平扩展           会话以 JWT 承载，锁定计数存放于 Redis

  数据隔离默认开启   客户数据隔离是默认行为而非可选配置             订单查询统一注入 user_id 条件，从框架层杜绝越权

  依赖最小化         本期不引入支付等外部服务，保持链路简洁         订单金额由舱位与票数计算得出，仅作展示，不产生资金流

  安全默认           认证、加密、审计能力默认开启                   除注册、登录、安全问题重置外全量接口需鉴权；密码与安全问题答案 BCrypt
                                                                    加密存储

  可追溯             关键操作与状态流转留痕                         订单状态每次变更写入流转记录表；注册、登录、下单、改单、取消写入操作日志
  --------------------------------------------------------------------------------------------------------------------------------------------

- 后端可替换为 Python（Django / FastAPI）或
  Node.js（NestJS）：分层结构、数据模型与接口契约保持一致，仅需替换基础设施层实现。

**5 数据架构**

**5.1 实体关系**

系统核心业务实体为客户（user）、城市（city）、航班（flight）、订单（orders）；另设订单状态流转表（order_status_log）与管理支撑实体管理员（admin_user），分别服务流转留痕与后台管理。一名客户可拥有多张订单；一张订单关联一个航班、一个出发城市与一个到达城市。

  ------------------------------------------------------------------------
  **关系**        **基数**   **说明**
  --------------- ---------- ---------------------------------------------
  user → orders   1 : N      一名客户可有多张订单，订单强绑定 user_id

  flight → orders 1 : N      一个航班可被多张订单引用

  city → orders   1 : N      订单分别引用出发城市与到达城市（两个外键）
  ------------------------------------------------------------------------

**6 接口设计**

**6.1 接口约定**

- 协议与格式：HTTP + JSON，字符编码 UTF-8。

- 基础路径：/api。除注册、登录、安全问题获取与密码重置外，其余接口均需在请求头携带
  Authorization: Bearer \<token\>。

- 统一响应结构：{ code, message, data }，code 为 0 表示成功，非 0

  401；越权访问返回 403 并统一提示「订单号不存在」。

- 管理端接口：/api/admin/\*\*
  使用独立的管理员令牌，与客户侧令牌体系隔离，互不可用；管理端操作全部记录审计日志。

**7 关键设计**

**7.1 认证与会话**

1.  注册：校验通过后写入 user 表，密码与安全问题答案分别经 BCrypt
    加盐哈希存储，系统不保存明文，也不提供反查。

2.  登录：严格按「用户名为空 → 密码为空 → 用户名格式 → 密码格式 →
    账号锁定状态 →
    密码比对」顺序校验（BR-06：两者同时为空时优先提示「请输入用户名」）；密码以
    BCrypt 比对，区分大小写由配置项 password.case-sensitive
    控制（LR-10）。校验通过后签发 JWT，有效期 2 小时，携带 userId 与
    username。

3.  锁定：以 username 为键在 Redis 累计连续失败次数（INCR，TTL 15
    分钟），达到 4 次时回写 user.fail_count 并写入 locked_until =
    当前时间 + 15 分钟（LR-12）；锁定期间一律拒绝登录并返回 1107
    及剩余解锁秒数（LR-13）；登录成功或锁定到期后同时清零 Redis
    计数与数据库 fail_count、locked_until。用户名不存在时仅在 Redis
    计数、不回写数据库，并统一按「密码错误，请重试」提示，避免账号枚举。

4.  登出：将令牌加入 Redis 黑名单并在剩余有效期内拦截，实现主动失效。

5.  密码重置：答案去除首尾空格并统一大小写后与 BCrypt
    密文比对（UR-10）；同一用户名连续答错 3 次，以 reset:{username}
    记录在 Redis 并按自然日 24:00
    过期，当日禁止再次重置（UR-11）；新密码须满足强度规则，且不能与用户名相同、不能与当前密码相同（UR-12）；重置成功后写入新密码密文，并使该用户已签发的全部令牌失效（UR-13）。

6.  预设安全问题：由 SecurityQuestionPresets
    常量提供系统预设问题列表（如「您母亲的名字是？」「您的小学校名是？」「您最喜欢的城市是？」「您的第一辆车品牌是？」「您最好的朋友名字是？」），注册与重置共用同一列表；答案
    BCrypt 加密存储，接口只回显问题、不回显答案（UR-04、UR-09）。

7.  令牌续期：登录响应同时返回令牌过期时间戳，前端临近过期调用 API-16
    续期；登出与密码重置后令牌立即失效，续期失败则跳转登录页重新认证。

8.  演示账号：测试环境可保留密码为 123456
    的演示账号；该账号不进入生产环境，且不作为全系统默认密码。

**7.2 数据隔离与越权防护**

- 服务端从 JWT 解析 userId，所有订单查询与操作均自动附加 user_id
  条件，不接受客户端传入的用户标识。

- 在数据访问层统一封装：OrderMapper 的所有方法均要求传入 userId
  参数，从框架层杜绝漏加条件。

- 访问他人订单时统一返回「订单号不存在」，避免通过响应差异探测他人订单是否存在。

- 测试阶段必须包含越权用例：以用户 A 的令牌访问用户 B 的订单号，预期返回
  403 或「订单号不存在」。

- 管理端隔离：管理员使用独立账号表 admin_user 与独立令牌，/api/admin
  前缀单独鉴权；管理端令牌不能访问客户侧接口，客户令牌不能访问管理端接口，管理端操作全部写入审计日志。

**7.3 订单状态机**

![架构图](media/344be1d4cdd5df77d093edd03b6e8a72e772d8d6.png "架构图"){width="5.208333333333333in"
height="2.0416666666666665in"}

图 2 订单状态机

- 状态定义：TICKETED（已出票，下单成功即进入该状态）→
  DONE（已完成）；TICKETED 可流转为 CANCELLED。

- 流转控制：由 OrderStateMachine
  统一管理，定义每个状态允许的下一个状态集合；非法流转直接拒绝并返回错误码。

- 前端不提交目标状态，只提交动作（下单、取消），由服务端决定目标状态。

- 并发安全：状态流转与订单更新使用乐观锁（version）配合条件更新，防止并发操作相互覆盖。

- 自动完成：定时任务每日扫描 flight_date 早于当前日期且状态为 TICKETED
  的订单，批量变更为 DONE。判定口径统一为「航班日期当日 24:00
  已过」，不取 depart_time
  时刻，避免与下单日期校验（OR-01、OR-02）产生歧义。

- 流转留痕：每次状态变更写入 order_status_log，记录
  from_status、to_status、action、operator_type（USER / SYSTEM /
  ADMIN）、operator_id 与 operate_time；定时任务批量置为完成时
  operator_type 记为 SYSTEM。

- 修改实时校验：更新订单除校验状态为 TICKETED 外，还须校验 flight_date
  晚于系统当前日期，避免定时任务尚未执行时允许修改航班日期已过的订单（OR-18、OR-19）。

- 入口控制：仅 TICKETED 且航班日期未到的订单提供修改与取消入口；DONE 与
  CANCELLED 订单前端不渲染入口，服务端状态机同步拒绝（OR-27）。

- 航线一致性：修改起终点后，flight_id
  必须属于新起终点对应的航线；不满足时按新建时的同类错误提示拒绝保存，避免订单出现航线与航班不匹配（OR-18、OR-20）。

**7.4 校验规则实现**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **规则**           **实现位置**                     **校验逻辑**
  ------------------ -------------------------------- ------------------------------------------------------------------------------------------------------------------------------------
  用户名             UsernameValidator（服务端） +    长度 4～8；正则 \^\[0-9A-Za-z\]{4,8}\$；\^(?!\\d+\$) 排除纯数字；\^(?\![0-9\]) 排除数字开头；判空优先；唯一性查库
                     前端同规则校验                   

  密码强度           PasswordPolicy                   8～20 位；必须同时包含字母与数字；不能与用户名相同（1010）；拒绝连续与重复字符，如
                                                      12345678、aaaa1111（1011）；重置场景另校验不能与当前密码相同（1205）

  安全问题           SecurityAnswerPolicy             注册时问题必选、答案必填且长度 2～30 位；答案 BCrypt 加密存储；校验时统一去除首尾空格并转大写后比对密文；连续答错 3 次当日禁止重置

  航班日期           FlightDateValidator              先校验 mm/dd/yy
                                                      格式与日期合法性，格式非法提示「航班日期格式不正确，请按mm/dd/yy输入」（3008）；再按自然日与系统当前日期比较，不晚于当前日期则提示
                                                      3001「此日期后的航班日期有效 + 系统日期」（OR-01、OR-02、OR-16）

  起终点             CityValidator                    fromCity 与 toCity 不相等；前端在目的地下拉中过滤出发城市

  票数与总价         PriceCalculator                  total = unitPrice(seatClass) × ticketCount；票数默认 1、上限
                                                      9，超出提示「单次最多可预订9张机票」（3007）；舱位或票数变更后服务端重算并回写（OR-22）

  订单号             OrderNoGenerator                 新建时生成，更新接口不接收 orderNo 字段

  订单号检索         OrderService +                   订单号输入框允许输入任意字符（含非数字），格式不在前端拦截，由服务端查询阶段判定；未命中一律返回「订单号不存在」（OR-17）
                     OrderMapper（查询阶段）          

  航线与航班一致性   OrderUpdateValidator（服务端）   修改起终点后校验 flight_id 属于新航线；不满足则复用新建时的错误提示，不允许保存（OR-18、OR-20）
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

校验采用「前端即时校验 +
服务端强制校验」双重机制：前端负责交互体验，服务端作为最终防线，两者共用同一套规则描述，避免规则漂移。

**7.5 订单号生成**

- 订单号：业务前缀 + 日期 + 序列，例如 FR202609170001，序列由 Redis
  自增或数据库序列表保证唯一。

- 唯一性保障：订单号建唯一索引，生成冲突时重试，最多 3 次。

**7.6 异常处理与提示语**

- 定义统一业务异常 BizException，携带错误码与提示语，由
  GlobalExceptionHandler 转为统一响应。

- 所有提示语集中在 messages 配置（如
  user.name.empty、order.date.invalid），与需求文档中的中文文案一一对应。

- 未知异常统一转为「系统繁忙，请稍后再试」并记录完整日志，避免向用户暴露系统细节。
